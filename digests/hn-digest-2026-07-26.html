Kill The Cookie Banner

1,050 points · 496 comments · killthecookiebanner.eu

What the comments said

2 Security

GrapheneOS protections against data extraction from locked devices

416 points · 231 comments · discuss.grapheneos.org

A GrapheneOS forum discussion explains the security-focused Android fork's defenses against forensic data-extraction tools used by law enforcement and border agents on locked phones. Key mechanisms discussed include duress PINs/passwords that wipe the device rather than unlock it, and an auto-reboot feature (configurable down to 10 minutes, default 18 hours) that returns a device to Before First Unlock (BFU) state, where encryption keys cannot be extracted even with hardware exploits. The thread appears tied to two real news events: a US prosecution of a man who allegedly used a GrapheneOS duress PIN during a border search, and a journalist crediting the auto-reboot feature with protecting sources after a phone seizure.

What the comments said

  • Commenters connect the thread to a real prosecution: a US man is being charged after allegedly giving border agents a GrapheneOS duress PIN that wiped rather than unlocked his phone, sparking debate over whether using security features can itself become criminalized.
  • Practical tips circulate widely: users recommend temporarily shortening the auto-reboot timer (down to 10 minutes) before border crossings or protests, and manually rebooting to force the phone into BFU mode where keys are inaccessible.
  • A GrapheneOS official account quoted in the thread pushes back on requests for stealthy 'decoy' wipes that fool an inspector into thinking the phone is normal, stating the duress feature intentionally does not offer plausible deniability and that legal-strategy questions are outside the project's scope.
  • Sizable side-debate on password/pattern strength: commenters calculate that Android's pattern lock offers very low entropy (~18.6 bits) and discuss GrapheneOS's long-passphrase-plus-fingerprint-PIN scheme and hardware brute-force throttling as mitigations, with some correcting claims that long passwords aren't supported.
  • Several commenters raise the unsolved problem of no robust encrypted backup/restore solution, with users wanting to wipe phones before travel and restore afterward; others note a SeedVault replacement is in progress, and some argue a nearly-empty phone would itself look suspicious to inspectors.
3 Programming

Go Analysis Framework: modular static analysis by go team

212 points · 70 comments · pkg.go.dev

This is the pkg.go.dev documentation for golang.org/x/tools/go/analysis, the Go team's standard interface for writing modular static-analysis checkers. An Analyzer describes a self-contained check (like the printf format-string checker) with a name, flags, and a Run function operating on a Pass, which supplies parsed syntax trees, type information, and a Report function for diagnostics. Because analyzers can declare dependencies on each other (Requires) and share cross-package facts, the same checker logic can be reused across vet, IDEs, build systems like Bazel, code-review tools, and other driver programs without each reimplementing analysis plumbing.

What the comments said

  • Multiple commenters note the framework isn't new at all (it underpins many existing Go linters already) and question why it's being resubmitted now; the consensus answer is it was mentioned in a Ruff discussion thread where people wished Go had similar tooling, unaware this already existed, prompting a dedicated repost.
  • A real-world endorsement: an engineer from SpiceDB says their team has used the framework successfully to write custom analyzers, and argues LLMs make writing new analyzers roughly 10x easier now, reducing reliance on tribal knowledge in code review.
  • A tangential but heated sub-thread breaks out over Go generics and error handling verbosity, with defenders of Go's manual loops and explicit error wrapping sparring sarcastically with people who find the style tedious compared to standard-library helpers like slices.Contains.
  • One commenter frames the broader theme as the Go team's unusual investment in tooling as a force-multiplier for both human developers and AI coding agents, citing patterns like Makefile-based 'tool calls' and build-tag-gated test suites that make agentic iteration faster.

6 Programming

A shell colon does nothing. Use it anyway

389 points · 171 comments · refp.se

The article is a tour of POSIX shell's colon (:) 'null command,' a builtin that does nothing but evaluate its arguments and discard the result. The author shows how combining it with parameter expansion enables compact idioms: `: "${1:?missing argument}"` replaces a four-line argument-check if-statement, `: "${VAR:=default}"` sets a default while mentioning the variable name only once, and the colon can be used anywhere a shell command is syntactically required but no action is wanted — truncating files via redirection, checking readability/writability, or serving as a placeholder branch in an if/else. An added FAQ section (updated after publication in response to reader feedback) addresses why the null-command is needed at all versus plain expansion or `VAR=${VAR:-default}`.

What the comments said

  • Reaction is split: many commenters find several of the tricks (like the `:?` required-argument check) genuinely useful, especially for validating environment variables, while others — including one comparing the colon to 'the appendix of the shell' — find the terse style actively harmful to readability.
  • The article's author (refp) is actively present in the thread, engaging with critiques, updating the post in response to at least one comment (adding a named-variable example), and clarifying that examples like file truncation were intentionally tongue-in-cheek rather than production advice.
  • A commenter offers a substantive technical critique of the truncation example: it silently creates a file if absent rather than merely truncating, and works identically without the colon at all, arguing the article missed a chance to explain that redirection happens before command execution.
  • A broader recurring debate throughout the thread contests whether Bash is worth learning these idioms for at all, with a vocal contingent arguing any script beyond a couple lines should be rewritten in Python or Perl — while others counter that LLMs are now quite capable of writing correct Bash, reviving interest in its more obscure features.
  • Multiple commenters share their own preferred alternative idioms and style conventions (e.g., `TARGETFILE="${1:?...}"` for named variables) and debate the tradeoffs between explicit if/else negation versus colon-as-placeholder patterns.

Design is compromise

  • Several commenters debate semantics: some distinguish "compromise" (multi-dimensional optimization under constraints) from the colloquial negative sense of skimping on cost, effort, or attentiveness.
  • A popular sub-thread argues optimization inherently requires compromise once you have multiple competing goals, since you must weight one objective against another rather than get a free win.
  • Others push back that the essay's claim is almost tautological/not very remarkable, since it's obviously true that optimizing for everything simultaneously is impossible.
  • A recurring theme is that compromise has become culturally stigmatized as a sign of weakness, with commenters sharing personal/career reflections on learning to embrace compromise as a valuable skill.
  • One thread distinguishes true compromise (a lose-lose split of differences) from a win-win "mutual preference" reached through creative problem-solving, arguing these are often conflated.

9 Embedded AI

Running a 28.9M parameter LLM on an $8 microcontroller

277 points · 70 comments · github.com

A developer got a 28.9M-parameter language model running entirely on an $8 ESP32-S3 microcontroller at about 9-9.5 tokens/second, roughly 100x more parameters than the previous record for a chip this small (260K params). The trick, borrowed from Google's Gemma "Per-Layer Embeddings" technique, is to keep the 25M-row embedding table in slow flash storage (pulling only ~450 bytes per token) while keeping the small compute-heavy "thinking" core in fast SRAM. The model, trained only on the TinyStories dataset, can write short coherent stories but cannot answer questions, follow instructions, or know facts.

What the comments said

  • Commenters were broadly impressed and enthusiastic, praising the per-layer-embedding trick as a clever, apparently novel application to microcontroller-scale hardware.
  • Several suggested follow-on applications, like pairing this with small (~20-30M param) offline text-to-speech models for a fully network-free reading device.
  • A technical sub-thread explored whether the flash-backed-embedding idea could scale to much larger models on desktop CPUs; one commenter cited a related project (colibri) running a large model off NVMe/RAM at ~10-20 seconds per token, and others explained the ESP32's flash bandwidth (about 1/4 of its SRAM) as the limiting factor.
  • A tangential but active thread discussed the ESP32-S3 chip itself as a cheap, capable dev tool (e.g., dual USB ports enabling OTG tricks), with comparisons to doing similar cheap USB tricks on the even cheaper RP2350.
