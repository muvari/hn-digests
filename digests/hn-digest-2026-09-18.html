OpenJev

638 points · 270 comments · openjev.com

Photon-Emission-Guided Laser Fault Injection Enables RP2350 Secure Debug

195 points · 73 comments · donjon.ledger.com

Ledger's Donjon team used photon-emission microscopy to locate the exact register on Raspberry Pi's RP2350 controlling debug access, then used targeted laser pulses to flip that register and restore Secure-world debugger access despite debug being permanently fuse-disabled. Combined with a rescue reset that halts the chip before firmware reapplies its runtime lock, they extracted a 128-bit secret from supposedly inaccessible one-time-programmable memory — though the attack requires physical possession, destructive decapsulation, and roughly $250,000 of lab equipment.

  • People appreciated the deep technical writeup and drew parallels to older physical side-channel tricks like imaging with decapped DRAM chips.
  • A few joked about implications for Apple devices and other secure-enclave products relying on similar physical protections.

23 Programming

C++26: Trivial infinite loops are no longer undefined behaviour

162 points · 248 comments · sandordargo.com

Before C++26, a trivial infinite loop like while(true); with no side effects was technically undefined behavior, since the forward-progress guarantee let compilers assume every thread eventually terminates or does I/O — meaning optimizers like Clang could remove such loops entirely, letting execution fall through into whatever code was linked next. C++26 (via P2809R3) fixes this: a narrowly defined "trivial infinite loop" is now well-defined, compiling to std::this_thread::yield(), closing a real embedded/kernel hazard where a halt-on-fatal-error loop could silently fail to actually halt.

What the comments said

  • Commenters were struck by the concrete "Hello world!" demo of a program falling through into an unrelated function — a class of bug (missing return, unintended fallthrough) several said they've personally hit.
  • A vocal contingent was frustrated the standard allowed this hazard for 15 years given its danger in embedded fault-handling code; others defended the original design as enabling legitimate optimizations.
  • People noted C actually got this right from C11 onward, and debated why C++ never adopted C's broader protection.
  • A tangent explored why an unreachable function even remains in the compiled binary, with explanations about how machine code has no inherent concept of "functions."

Cyclomatic Complexity in C#

68 points · 25 comments · blog.ndepend.com

An NDepend post explains Cyclomatic Complexity — a 1976 McCabe metric counting linearly independent paths through a method, computed as 1 plus the number of branches (if, while, for, case, &&, ||, ternaries, etc.) — with a worked C# example scoring 8, then shows splitting it into smaller methods to reduce each piece's complexity. The post frames CC as meaningful because it equals the minimum test cases needed to exercise every independent path, recommending it be paired with test-coverage and IL-level analysis.

What the comments said

  • Commenters pointed out CC's well-known blind spot: designed before polymorphism was common, so virtual calls or higher-order functions don't increase the score even though they can hide unbounded complexity.
  • Some pushed back on the article's own refactoring example, arguing splitting a method can trade lower CC for worse readability by forcing readers to jump between functions.
  • A few developers described integrating CC and dependency-graph analysis into agentic coding workflows as an automated quality gate for catching AI-generated code that strays from established patterns.
  • One commenter cited EEG-based cognitive-load research suggesting standard complexity metrics only partially predict how hard code is for humans to understand.

How Uber Protects Against Retry Storms

114 points · 49 comments · uber.com

An Uber engineering post explains how uncoordinated retries across deep service chains create "retry storms": if every hop in a 6-service chain retries once on failure, request volume can amplify exponentially with chain depth by the time it reaches the failing service. Uber's fix, "error ownership," has infrastructure distinguish whether a service's error is a genuine "cause" versus merely a passed-through "symptom," and only allows retries at the edge where the error actually originates — keeping amplification near the origin instead of compounding at every hop.

What the comments said

  • Engineers shared hard-won retry lessons, including horror stories of naive "retry everywhere" policies compounding catastrophically, asking for a middle ground between global retries and only retrying at the top of a chain.
  • Multiple people noted load shedding and adaptive concurrency limiting (which Uber and Netflix separately publish systems for) are complementary techniques the post doesn't fully cover.
  • Some compared "error ownership" favorably to SRE error-budget thinking, while others noted it resembles established flow-control mechanisms like Fibre Channel's.
  • A commenter argued a token bucket alone doesn't solve cascading amplification, since every hop retrying independently at its own rate limit can still multiply across a deep chain.
