Spymarks, not Watermarks

667 points · 165 comments · brand.io

The author coins the term "spymark" to distinguish hidden, non-consensual tracking signals embedded in AI-generated media (via tools like Google's SynthID) from traditional, benign visible watermarks. Spymarks can encode database identifiers linking a piece of content back to a user's identity — name, address, IP, date of birth — and the piece shows SynthID reportedly fitting a 136-bit payload into a single image. It argues a distinct, negatively-loaded name clarifies the privacy stakes, citing decades-old printer tracking dots as precedent, and contrasts spymarks with user-editable metadata like EXIF or ID3 tags.

What the comments said

  • Several commenters note that "watermark" has long colloquially covered hidden tracking uses (digital download watermarks, movie screener marks), questioning whether a new term is needed.
  • Some pushed back on the "spymark" label itself as needlessly pejorative, since not all invisible watermarks are malicious (e.g. anti-counterfeiting on banknotes); a proposed alternative, "steganomark," was called more accurate but too technical to catch on.
  • A thread on whether spymarks can be defeated (analog copies, re-encoding, AI paraphrasing) was met with clarification that text watermarks are embedded in word choice itself, so copy-pasting text doesn't strip them.
  • Discussion broadened into general unease about ambient surveillance — smart TVs, in-car monitoring, smart glasses — with several arguing microphones are a far bigger, underappreciated threat than cameras.
  • One commenter flagged an angle the article didn't explore: this technology's potential use to unmask whistleblowers.

WordPress: Unauthenticated path traversal leading to conditional RCE

210 points · 106 comments · github.com

A GitHub security advisory discloses a critical (CVSS 9.2) unauthenticated path traversal flaw in WordPress core's page-template resolution, affecting essentially every release back to version 4.7. Exploitation requires the active theme to have a top-level directory prefixed "page-" (common in themes like Twenty Twelve, Twenty Fourteen, Neve, Hestia, and Sydney) plus a readable local PHP file to target, such as via the well-known pearcmd.php PEAR-to-RCE trick when register_argc_argv is enabled — a configuration present in the official PHP Docker image and default cPanel setups. What the comments said

  • Commenters split on severity: some argue the CVSS score overstates real-world risk since exploitation needs specific theme conventions, while others counter that the "page-" prefix is an officially documented WordPress convention, so far more themes qualify than the skeptics assume.
  • Several flag that the official PHP Docker image and default cPanel configurations meet the vulnerable preconditions out of the box, raising concern for containerized and hosted deployments.
  • One commenter surfaces a nine-year-old warning on the WordPress docs page for locate_template() that explicitly describes this exact traversal risk, suggesting the flaw was long foreseeable.
  • General cynicism about WordPress's (and PHP CMS software's) long history of exploits, with comparisons to Joomla and jokes about web server logs full of scripted exploit probes.

Can gzip be a language model?

392 points · 154 comments · nathan.rs

Building on the "compression is prediction" equivalence from the paper "Language Modeling is Compression," this post asks whether gzip's DEFLATE algorithm can generate text. The author primes gzip with a corpus (tiny Shakespeare) and generates continuations via beam search, scoring candidate byte sequences by how small they make the corpus-plus-text compress, since DEFLATE encodes corpus-like text cheaply as back-references. Naive single-byte generation fails due to integer-length quantization noise, so the tool ("gzipt") searches ahead over multi-byte spans and keeps only a sliding window of recent output to avoid collapsing into verbatim repetition loops, producing text that isn't coherent but is recognizably Shakespeare-flavored, all from one small pure-Python file.

What the comments said

  • Several commenters question whether the beam search actually finds good optima, noting the context window was specifically limited to avoid the method degenerating into repeated "aaaa" runs — which they say undercuts the "gzip is basically a language model" framing.
  • A broader debate contrasts gzip and LLMs as "wildly different animals": gzip has no attention mechanism and only a 32KB window, scaling linearly, while LLM-style comparisons work better with lossy codecs like JPEG/MP3 than with lossless gzip.
  • Others point out that neural-network-based compressors already top benchmarks like the Hutter Prize, suggesting the inverse question — how well LLMs compress — is well established.
  • A tangent explores practical use as a lightweight classifier, e.g. compression-ratio-based spam detection, with pointers to prior art using LZO and zstd for text classification.
  • A link is shared to a previous HN discussion of the same author's earlier from-scratch n-gram language modeling post.

17 Security

SAML: A fractal of bad design

275 points · 148 comments · blog.trailofbits.com

Trail of Bits argues that SAML, the XML-based SSO protocol born from a 2002 standards-committee merger of four competing proposals, should be retired in favor of OpenID Connect. The post traces SAML's rise through academia and SSO vendors like Ping, OneLogin, Okta, and Duo, then details its core weakness: it depends on notoriously complex and error-prone XML signature validation, illustrated by XML signature-wrapping (XSW) attacks first documented in a landmark 2012 paper that remain exploitable in some implementations today, on top of XML's broader history of vulnerability classes (XXE, entity expansion, DTD/SSRF injection). Drawing on the author's own years building Duo's early SAML-based SSO gateway, the piece concludes SAML's committee-driven complexity makes secure implementation unreasonably hard even over a decade after these flaws became public.

What the comments said

  • Many commenters agreed SAML is bad but pushed back on treating OAuth2/OIDC as a clean fix, with some calling OAuth2 "shite" and others clarifying it's an authorization protocol misused for authentication while OIDC is the true replacement.
  • A recurring practical complaint was vendor lock-in: enterprises often can't drop SAML support because large customers simply demand it, regardless of the security tradeoffs.
  • Commenters extended the "design by committee" critique with analogies to OpenVPN vs. WireGuard and OSI vs. IP, which spun off a side-debate over whether XML is unfairly maligned relative to JSON.
  • Several people argued that identity and authentication for AI agents is the next unsolved frontier, contending that OAuth/OIDC are already showing similar cracks there.
  • One suggestion was for implementers to support only a curated subset of SAML dialects used by top providers rather than full general-purpose XML parsing, though others questioned whether a trustworthy library for that subset even exists.
