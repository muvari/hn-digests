2 Security

Telegram Desktop vulnerability allowed any user's file to be stolen

454 points · 298 comments · beaksec.github.io

A researcher found that Telegram Desktop hands clicked tg:// links to its already-running instance as raw text over a local socket, without escaping the semicolon used to separate internal commands — letting one crafted link inject several. That injection reaches an internal "interpret:" URI scheme, originally built so Telegram's own team could publish release files to a channel, which reads a named file and uploads it to a chat with no confirmation, turning a single click into arbitrary local file theft and account takeover. Fixed in 7.2.9 (CVE-2026-107181, CVSS 8.1).

What the comments said

  • Many note the root cause — "interpret:" — was a tool Telegram's own developers built to upload arbitrary files for their release process, calling it an almost absurdly convenient design to later exploit.
  • A sizable thread argues this is really a consequence of desktop OSes letting any user process read/write any user file, though others push back that Telegram still can't blame the OS for silently exfiltrating that file.
  • Old reputational skepticism about Telegram's security resurfaces, but commenters distinguish protocol/infra criticism from this being a genuinely new file-exfiltration bug.
  • Practical sandboxing suggestions (bubblewrap/jailed launch commands) are floated, though some note that alone wouldn't have stopped the account-takeover piece, which relies on Telegram's own session files.
  • A side discussion on how exposed phone-number-based accounts already are by default, with notes about login notifications and the password/2FA feature mitigating full takeover.

20 Systems

Unikernels were hard. key word: were

177 points · 89 comments · ghuntley.com

Recapping a conversation with MirageOS veteran Justin Cormack, Geoffrey Huntley argues unikernels — "OS-less" systems where the application is its own operating system, with no shell or userland to fall back on — were historically painful because every bit of infrastructure (TCP stacks, storage drivers) had to be hand-written as a library. He argues AI coding agents now make that tractable: porting a missing library (like Stripe bindings) or reverse-engineering a byte-identical Rust reimplementation of `mkfs.xfs` against a reference "golden oracle" is now a loop an agent can run, while the lack of a shell or interpreter also denies attackers (human or AI) anywhere to pivot after a compromise.

What the comments said

  • Security-focused commenters argue "attack surface reduction" understates the real benefit — removing the multi-tenant OS model entirely — while others counter that memory-corruption and gadget-based exploits still work regardless of unikernel isolation.
  • A substantive thread clarifies unikernels still reuse shared, reviewed library code rather than hand-rolling filesystems and networking per application; they just redraw where the abstraction boundary sits, replacing syscalls with plain subroutine calls.
  • Debate over whether fast microVM boot times (cited via Netlify and Unikraft) matter for most workloads, versus being valuable mainly in niche, high-density multi-tenant job-scheduling scenarios.
  • Concerns about debuggability when a single buffer overflow can corrupt the whole single-address-space "kernel," with mixed views on whether current unikernel debugging tooling (gdb stubs, etc.) is adequate.
