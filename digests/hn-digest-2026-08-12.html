1 Databases

Tracking down the 16-year-old WAL-reset SQLite bug

1,019 points · 188 comments · tailscale.com

Tailscale describes a year-long ordeal in which its SQLite-backed control-plane shards suffered 19 separate database corruption incidents, each requiring the shard's control plane to go offline for repair. Despite an unremarkable single-writer SQLite setup and no relevant recent code changes, the corruption had no reproducible trigger, forcing the team to build passive forensic telemetry to catch it "red-handed" in production. The investigation eventually implicated a genuine 16-year-old race condition in SQLite's WAL checkpoint-reset logic, which Tailscale helped isolate by funding an open-source SQLite VFS debugging shim; the bug required multiple connections to the same database file and was made far more likely by Tailscale's unusually aggressive manual checkpointing.

What the comments said

  • Many commenters praised the postmortem's transparency and Tailscale's decision to fund an open-source SQLite debugging tool and pay for a SQLite support contract, framing it as a model of healthy engineering culture.
  • A close technical thread questioned the "single-writer design is exactly how SQLite is meant to be used" framing, since the bug requires multiple connections open on the same file — implying the writer and checkpointer ran on separate threads, contrary to the simplest reading of the post.
  • Some pushed back that at Tailscale's scale, a heavier database like Postgres or MariaDB might have been the more appropriate choice, since SQLite is explicitly meant to be "lite."
  • Commenters noted the post explains why Tailscale specifically got hit so hard: their aggressive, manually-controlled checkpointing made a rare timing-dependent race far more likely to trigger than for typical SQLite users.
  • Others discussed the general difficulty of chasing irreproducible data-corruption bugs, noting it's a fairly common (if painful) category of problem in storage systems, and pointed out the underlying single-shard failure mode as a broader architectural weak point.

6 Computer Science

Compression is prediction

650 points · 279 comments · ngrok.com

The post walks through the mechanics of data compression — transforms, statistical models, and entropy coders — building up from simple run-length encoding to arithmetic coding, which represents an entire dataset as a single number derived from symbol probabilities. Its central thesis is that compression and language modeling are fundamentally the same problem: both work by building a probability model over symbols and using better probability estimates to squeeze out redundancy, meaning a sufficiently good compressor is, in effect, a language model (and vice versa).

What the comments said

  • Multiple commenters pointed to Grant Sanderson's (3Blue1Brown) "Compression is Intelligence" video series covering closely related ground, and wondered whether the two pieces were developed independently.
  • A substantive debate emerged over whether framing LLMs as compressors undermines "just next-token-prediction" dismissals of LLM creativity — some argued training-as-compression-search makes emergent "new ideas" more plausible, while others pushed back that genuinely new ideas by definition aren't in the training distribution, so the compression framing doesn't resolve the question.
  • Several technically-minded replies emphasized the equivalence is bidirectional and exact: any compressor (even gzip) can be trivially turned into an autoregressive generator by compressing "context + candidate token" for every possible next token and picking the least-surprising one, though the output quality is far worse than a trained transformer.
  • One commenter cautioned against over-reading the equivalence — LLMs are compressors, but naive compressors can't do what LLMs do — while also noting related work injecting n-gram statistics directly into network weights.
  • A few readers noted the article surprisingly omits any mention of embeddings or autoencoders, despite both being commonly framed as compression techniques directly relevant to the piece's argument.

13 Web & Browsers

Why tiny JPEGs look different in Chrome

297 points · 64 comments · guillaumetech.github.io

The author noticed a small JPEG icon rendered thinner and more faithful on a colleague's machine, and traced the difference to a Chrome/Skia optimization: instead of fully decompressing a JPEG and then scaling it down, Chrome's libjpeg-turbo uses "partial IDCT scaling" to decode only the low-frequency DCT coefficients when the target size is small enough (fractions with a denominator of 8), discarding high-frequency detail before the image is even decoded. This saves memory and CPU (a 2000x2000 JPEG scaled to 20x20 would otherwise require a ~12MB intermediate bitmap) but produces a visibly softer, thicker-looking result at tiny sizes, whereas Firefox streams and downscales during decode without this coefficient-skipping trick. The author's takeaway: JPEG's optimizations are built around photographic content, so icons are better served by SVG or PNG.

What the comments said

  • Commenters filled in the Firefox side of the story: it uses "downscale-during-decode," a streaming decode with on-the-fly downscaling, rather than partial 8x8-block decoding like Chrome, with a linked Bugzilla ticket on the technique.
  • Several argued the differing scaling algorithms (Chrome's blurrier approach vs. Firefox's sharper but more ringing-prone one) are a bigger contributor to the visual difference than the IDCT technique alone; the author added a correction to the post acknowledging this.
  • Some noted objective image-quality metrics tend to favor blur over ringing artifacts, even though subjective human preference often runs the other way.
  • One commenter shared a related Chrome/libjpeg-turbo bug where partial IDCT scaling can mix garbage data from unused trailing MCU rows/columns into visible artifacts, with links to the relevant Chromium and libjpeg-turbo issue trackers.
  • A tangent explored whether the same issue applies to PNGs; consensus was that PNG's block/palette structure doesn't support the same kind of partial decode, aside from the rarely-used Adam7 interlacing scheme.

194 points · 135 comments · en.andros.dev

The article argues for "HTML over WebSockets," exemplified by Phoenix LiveView (and similar frameworks like Django LiveView), as an alternative to the standard SPA architecture of a JS framework plus a JSON API. Instead of the client fetching JSON and rendering it, the server keeps a persistent bidirectional WebSocket connection, renders HTML on the back end, and pushes fully-built markup that the client simply inserts into the DOM, eliminating the need for an API contract and moving all state to a per-connection server process. The piece lays out the advantages (single rendering engine, no API layer, real-time broadcast to all clients, less per-action overhead than repeated HTTP requests) and positions it against HTTP-polling approaches like htmx and SSE-based approaches like Datastar.

  • Several disputed the article's latency claims specifically, arguing that modern HTTP/2/3 already multiplexes requests over persistent connections, so SSE plus fetch is simpler and just as fast for most apps unless request volume is very high; others countered that WebSocket's simpler framing still beats the full HTTP stack in practice.
  • Commenters raised operational concerns absent from the article: running a WebSocket server adds new failure modes (harder monitoring, two systems of truth, DoS/overhead risk) compared to a conventional, well-understood web server.
  • Multiple people noted the article omitted caching entirely and didn't mention WebTransport, which some see as a more modern, lower-latency bidirectional alternative already supported by all major browsers.

Mathematician Timothy Gowers, writing days after OpenAI announced solving ten major open problems (including a non-sofic group construction and a Ramsey-number growth bound), asks not whether LLMs are good at math but what kind of math they're good at. He observes that the highest-profile LLM results have mostly been counterexamples rather than proofs, then interrogates what "finding a counterexample" actually means using examples like Vinogradov's three-primes theorem and the Banach-Mazur distance, arguing the real question is which quantified variable in a multi-quantifier statement LLMs are suited to search over. He concludes that true human-level ability would show up as proofs using genuinely new, surprising methods that only look natural in hindsight, not the current pattern of search-heavy counterexample-finding.
