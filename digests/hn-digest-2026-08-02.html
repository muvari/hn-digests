Go 1.27 Interactive Tour

352 points · 188 comments · victoriametrics.com

VictoriaMetrics published a hands-on, runnable-example tour of what's new in the upcoming Go 1.27, picking up a tradition started by Anton Zhiyanov. The headline feature is generic methods: a method can now declare its own type parameters independent of its receiver, so operations like a generic Map transform can finally live as methods rather than package-level functions (though interfaces still can't declare generic methods). Other additions include struct literals that can key on promoted embedded fields, generalized function type inference in conversions and composite literals, size-specialized memory allocation that speeds up small allocations by up to 30%, and pprof goroutine labels now showing up in tracebacks and crash dumps.

What the comments said

  • A large thread expressed surprise that Go is still meaningfully expanding its generics support, with several asking what changed among the language maintainers; former Go team members explained it wasn't ideological resistance but that it simply took years of competing proposals to converge on a design everyone liked.
  • Reactions to the new generic-methods syntax were split — some found it made Go newly interesting to them, while others said the added complexity is exactly what pushes them away from the language.
  • A tangent asked whether generics could finally kill Go's `if err != nil` boilerplate; the consensus, including from an experienced Go contributor, was no — every Option/Result-style wrapper attempted so far trades convenience for safety in ways the community hasn't accepted, and the Go team has formally stopped pursuing syntactic error-handling changes.
  • A separate technical thread welcomed a fix enabling ARM Memory Tagging Extension (MTE) compatibility for gomobile apps, useful for hardened Android builds like GrapheneOS.
  • Some pushed back on general "Go bashing," arguing much of the criticism on HN is under-informed relative to the deliberate tradeoffs the language makes.

Show HN: Kakehashi – Experimental userspace to run macOS binaries on Linux ARM

222 points · 55 comments · github.com

Kakehashi is an experimental userspace translation layer, written in Rust, that loads Darwin Mach-O binaries and runs them natively on Linux aarch64 — no JIT, no kernel-level emulation. It works by mapping a freestanding libSystem, translating BSD syscalls, and bridging a "bottle" filesystem between host and guest. The maintainer reports working prototypes for 7-Zip (passing multithreaded compression tests, ~5.2x slower than native Linux), curl (200+ options passing automated tests), and early, not-yet-stable support for Xcode command-line Git tools.

What the comments said

  • Commenters drew comparisons to Wine/Proton's success translating Windows binaries and to the existing Darling project, which targets similar goals; the maintainer confirmed awareness of Darling but said Kakehashi's Rust, purely-userspace architecture is a deliberate departure from Darling's kernel-emulation approach.
  • Several people questioned how far the project can realistically go given the likely small universe of Mac-only CLI tools worth running on Linux, while others were enthusiastic about eventual GUI support or audio-plugin bridging similar to yabridge.
  • A notable thread pressed the maintainer on whether the project was a "clean room" implementation given heavy LLM assistance during development, since an LLM could plausibly have absorbed patterns from reading Darling's source; the maintainer called it a "light-gray room" effort, noting the from-scratch Rust codebase and explicit prompt restrictions against using proprietary components.
  • Several early testers said they'd be watching closely, citing macOS-version compatibility and future tool support as things they're waiting to see mature.

Developers are attached to tools because tools encode trust

216 points · 119 comments · stackoverflow.blog

The Stack Overflow blog argues that developer attachment to tools like Vim, Emacs, or a favorite IDE isn't nostalgia or stubbornness — it's accumulated trust and muscle memory built through predictable, stable tool behavior over years.   • Commenters described their own elaborate personal tooling setups (custom editors, keyboard firmware, browser automation) as evidence that ownership and control, not just habit, drive tool attachment.

179 points · 88 comments · fstar-lang.org

Nyctography: A substituton cypher by Lewis Carroll

81 points · 15 comments · en.wikipedia.org

Nyctography was a substitution writing system devised by Lewis Carroll in 1891 and used with a "nyctograph," a gridded card of quarter-inch square holes that let him write legibly in total darkness. Each symbol was anchored by a large dot in the upper-left corner of its square, letting the writer feel the starting point without seeing it, and the alphabet included extra glyphs for "the," "and," and markers indicating that following characters were digits, letters, or a date. Carroll invented it so he could jot down nighttime ideas without lighting a candle, and later suggested in an 1891 letter to The Lady that the same square-alphabet could be a boon to blind people wanting to write.

21 Security

RFC 10015: Deprecating Obsolete Key Exchange Methods in TLS 1.2 and DTLS 1.2

80 points · 22 comments · rfc-editor.org

RFC 10015 is a new IETF standards-track document (July 2026) that formally deprecates finite-field Diffie-Hellman (DHE/DH) and RSA key exchange in TLS 1.2 and DTLS 1.2, and discourages static ECDH cipher suites. It cites concrete attacks as justification: the Raccoon timing side-channel on reused DH public keys, invalid-curve attacks on ECDH, small-subgroup weaknesses in non-standard FFDHE groups, and RSA's lack of forward secrecy plus susceptibility to Bleichenbacher-style padding-oracle attacks.
