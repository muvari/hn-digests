18 Programming

How Swiss tables work in Go built-in map

102 points · 16 comments · victoriametrics.com

A deep-dive blog post explains how Go 1.24's built-in map switched to a Swiss Table-based implementation: entries are stored in 8-slot "groups" alongside a matching 8-byte control word, with each key's hash split into H1 (which group to search) and H2 (a 7-bit tag stored per slot, with the top bit flagging empty/deleted/live) so a lookup can rule out most slots with one control-word comparison before touching any actual keys.

What the comments said

  • Some highlight the practical payoff: comparing all 8 control bytes at once (effectively a SIMD-friendly scan) lets lookups skip empty slots without touching key memory, unlike the old chained-bucket implementation.
  • Requests for more top-down framing — what the overall structure looks like, why groups of 8, why this beats simple linear probing — before diving into byte-level control-word details.
  • A practitioner notes lookup speed isn't always the real-world bottleneck: for large maps with pointer-heavy keys/values, GC scan cost and memory footprint dominate, and asks whether Swiss tables help there.
  • A tangent notes Swiss Tables originated at Google (as did Go), prompting surprise it took this long to land in the standard map; replies point out Go predates the technique, and adoption required real engineering work.
