5 Programming

Making a Python interpreter in 1024 bytes

315 points · 110 comments · austinhenley.com

The author describes a weekend project writing a C program, squeezed into 1024 bytes, that interprets a small Python-like language: it supports def, colons, indentation-based blocks, and parenthesis-free if statements, enough to run a FizzBuzz example. Rather than compiling to an AST or bytecode like CPython, it's a recursive-descent parser that executes expressions as it parses, uses the C call stack for recursion, and implements loops by jumping backward and re-parsing the source each iteration. To hit the byte budget he applied classic C code-golf tricks: single-letter names, ASCII literals instead of character constants, implicit-int C89 declarations, and reusing globals and function parameters as scratch space.

What the comments said

  • A technical sub-thread discussed whether Python's significant whitespace makes writing a lexer meaningfully harder; several agreed it does, since it breaks regular-language lexing and requires tracking a stack of indentation levels (and even the exact sequence of tabs/spaces used).
  • Some commenters pushed back that this is "real" Python, arguing it barely supports more than the FizzBuzz example shown and would be more honestly called "Python-like."
  • Others drew comparisons to similar minimalist projects, like Snek (a tiny embeddable language for microcontrollers) and Justine Tunney's SectorLISP/sectorC boot-sector interpreters, debating how much a language can be stripped down before it stops being that language.
  • General praise for the writing and walkthrough quality was common throughout the thread.

bzip3

409 points · 119 comments · github.com

bzip3 is an open-source compressor billed as a "stronger spiritual successor to BZip2," combining a fast suffix-array-based Burrows-Wheeler transform, an LZ77/PPM-style run-length and context-modeling pass, and an order-0 context-mixing entropy coder.   • Some felt the "stronger than bzip2" claim needs more precise qualification, and that benchmarking parallel decompression against single-threaded bzip2 rather than pbzip2 also skews the comparison.

15 Security

Trusting-Trust Attack against an Entire Linux Distribution

220 points · 47 comments · arxiv.org

Researchers show Ken Thompson's classic "trusting trust" compiler backdoor isn't specific to compilers: they built a complete version of the attack using only GNU strip, an ordinary binary-stripping utility, without touching any source code. In NixOS's bootstrap process, a single tampered strip in the binary seed implants a payload that propagates across generations of rebuilt strip and survives even after the original tainted seed leaves the dependency closure — on a real nixpkgs revision it successfully built a full graphical installer with almost every binary backdoored.

What the comments said

  • Multiple commenters pushed back that the "specific to compilers" framing overstates the novelty: Thompson's original paper explicitly said the attack could apply to any program-handling program, and Paul Karger's earlier MULTICS security evaluation described the same class of attack a decade before Thompson.
  • A substantial thread debated whether Wheeler's "diverse double compiling" defense (rebuilding with independently sourced, diverse toolchains) can be extended to cover this attack by also diversifying the stripper/environment/hardware — with disagreement over whether that actually closes the hole or just moves the goalposts, and whether tainted-vs-clean binaries can even be meaningfully compared across divergent build environments.
  • Someone characterized the whole result more simply: if malware is already on your CI machine, it can infect build artifacts regardless of whether it masquerades as "strip" specifically; a reply countered that rebuilding strip from clean source doesn't clear the infection since the tainted copy modifies its own replacement.
  • A notable update: NixOS's x86_64/i686 bootstrap seed has since shrunk to just 181 bytes (via a recent nixpkgs PR), meaning the described attack surface mainly still applies to non-x86 platforms, and the commenter encouraged extending the research to those.

17 Programming

Simple Is Not Small

250 points · 82 comments · jyn.dev

Drawing on Rich Hickey's "Simple Made Easy" distinction between "sim-plex" (one braid) and "com-plex" (many braided together), the author argues simplicity is about decoupling, not size. A small Unix pipeline for word-frequency counting looks simple but is actually tightly coupled — sort | uniq -c ties aggregation to ordering, making a small feature change (preserving original order) require ugly temp-file joins — whereas a much larger program like Google Drive for Desktop can feel simple to its user because its internal complexity is well encapsulated. The piece concludes that building genuinely simple (large or small) systems requires actively decoupling features from each other, not merely splitting code into small pieces.

What the comments said

  • Many commenters treated Hickey's original "Simple Made Easy" talk as the definitive source and recommended watching it directly, with some saying it shaped their thinking on software more than almost anything else.
  • A recurring disagreement: several argued Unix pipes are "easy" and well-designed but genuinely not simple by this definition, since using them correctly requires handling exit codes, signal propagation, buffering, and partial writes — while others felt the real problem is that pipeline primitives are too inexpressive/limited rather than "coupled" per se.
  • Some readers found the essay's own Unix-vs-Clojure example contrived or unconvincing, calling the post more of a "Clojure is great" piece that takes "a swing and a miss" at fully capturing Hickey's point.
  • One thread extended the argument with a systems-thinking framing: Unix philosophy optimizes individual small tools ("rooms") without regard for the whole system ("the house"), whereas ecosystems like Clojure or Emacs are designed so each part improves the whole.
  • A practical anecdote: someone building a highly modular system said achieving true decoupling took multiple rounds of "trying and trashing" designs, and argued this is exactly why AI-assisted "vibe coding" works well for small isolated scripts but poorly for large, well-architected systems.
