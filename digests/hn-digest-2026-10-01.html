Why the Bronze Age Collapsed

403 points · 298 comments · worksinprogress.news

This Works in Progress piece argues the real mystery of the Bronze Age collapse isn't why empires fell around 1200 BC (droughts, invaders, and famine routinely cause upheaval without ending civilizations) but why no comparable empires re-formed for centuries afterward. The author's answer centers on metallurgy: bronze required scarce, long-distance-traded tin, which let elites monopolize weaponry, while iron — abundant and locally producible — "democratized" access to effective weapons once smelting techniques spread, permanently shifting the political equilibrium away from centralized imperial control.

What the comments said

  • Multiple commenters noted this "iron democratized violence" thesis isn't new, and some felt the article underweights competing explanations like the well-documented Sea Peoples migrations and collapsing Bronze Age trade networks (citing the Uluburun shipwreck as key evidence, which one reader noted is mentioned only obliquely in the piece).
  • A popular aside shared research suggesting early iron tools/weapons may have been forged from meteoric iron before smelting was mastered.
  • Several pushed back that iron weapons weren't inherently better than bronze — only cheaper and more available — and that pure (non-carbonized) iron is actually a poor tool material, with steel-making techniques developing only slowly after the collapse.
  • Others favored a multi-causal view: drought triggers unrest, newly-armed populations exploit weakened empires, supply chains cascade-fail, and bigger empires should have had resource advantages to recover but didn't.

RIP, vector database

354 points · 100 comments · turbopuffer.com

turbopuffer announces it is re-architecting its storage layer (v3) to stop treating the ANN vector index as the primary index that everything else — attribute filters, full-text search, aggregations — is built around. The company traces its history from a pure ID+vector store (v1) through added attribute filtering and BM25 full-text search (v2), explaining that keying every secondary structure off the vector's physical cluster address creates heavy write amplification and has hit diminishing returns, motivating a move to a general-purpose primary index with ANN demoted to "just another" secondary index.

What the comments said

  • Several commenters compared the shift to the classic Postgres-vs-MySQL indexing tradeoff: pointing secondary indexes at a stable row/doc ID (like InnoDB) versus at physical location, trading lookup cost for cheaper reindexing on write.
  • One detailed comment (apparently at least partly LLM-assisted, which others noted with amusement) connected the described "write amplification" problem directly to Uber's well-known 2016 Postgres write-amplification postmortem.
  • A turbopuffer engineer confirmed in-thread that the new primary key is an internal (segment ID, doc ID) pair, with the user-supplied document ID becoming a secondary index.
  • Broader skepticism that "vector database" was ever a coherent standalone category — several argued enterprise retrieval is better served by SQL databases or Elasticsearch/Vespa with vector search as just one query primitive alongside filters, joins, and ACLs.

14 Software

Git 3.0's upcoming SHA-256 default will be a costly mistake

463 points · 424 comments · blog.gitbutler.com

GitButler's Scott Chacon argues that Git 3.0's plan to make SHA-256 the default content hash (replacing SHA-1) will cause widespread, costly disruption for little practical benefit. He explains SHA-1 is "broken" only in the sense that deliberate collision attacks are now feasible with enough compute — but Git's real exposure is to second-preimage attacks, which remain practically infeasible for essentially any hash function in use, including SHA-1. Because SHA-1 and SHA-256 repositories are incompatible, he argues a default-flip will fragment tooling, break countless external hash references, and force costly whole-history rehashing for comparatively little real security gain.

What the comments said

  • A large contingent compared the migration unfavorably to IPv6 and Python 2→3: breaking changes, unclear benefit for most users, and no network effect forcing adoption, though others countered that each Git repo can migrate independently without affecting others, unlike IPv6.
  • Many pointed out the practical pain: external references to commit hashes in issue trackers, CI/CD caching, Slack/email threads, and submodules would all silently break after a rehash, with no built-in old-hash-to-new-hash lookup.
  • Author Scott Chacon (schacon) engaged directly in the thread, defending the piece against a "just set a config flag" counterargument by emphasizing that defaults matter at ecosystem scale, and linking to a talk explaining the technical issues with intermixing SHA-1 and SHA-256 objects.
  • A technical sub-thread debated whether SHA-256 repos could safely reference SHA-1 objects (and vice versa) via a migration window, with pushback that any single SHA-1 commit in a chain re-introduces the full forgery risk the migration was meant to close.
