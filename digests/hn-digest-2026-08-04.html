Show HN: Simple algorithm and color space to generate diverse skin tones

534 points · 92 comments · toneyalexander.github.io

The creator built a "good enough" mathematical color space for representing human skin tones, aimed at character creators, digital art, and similar tools that currently rely on either a handful of preset swatches or an unconstrained 16-million-color picker. Starting from manually labeled sample skin colors, they fit simplified equations defining a plausible region of RGB space, with a tunable "R²" radius that trades off between strict realism and a broader fantasy range (orcs, Na'vi, djinn). The author is explicit that the work is subjective, unscientific in its labeling process, and a starting point rather than an authoritative model, while providing JavaScript/Python code and an interactive picker.

What the comments said

  • Reception is largely enthusiastic, with developers who've built avatar or character-creator tools wishing they'd had something like this to replace hard-coded skin-tone options.
  • A recurring thread is tuning the R² radius: lowering it (to roughly 1.5) excludes implausible blue/green/purple outputs while still preserving realistic diversity, addressed directly in the page's methodology.
  • A researcher points to their own doctoral thesis showing skin color can instead be modeled in just two dimensions via melanin and hemoglobin concentration, offering an alternative, more principled approach.
  • Multiple commenters flag apparent color-rendering issues that turn out to just be dark-mode browser extensions altering the page, not flaws in the tool itself.
  • Several praise the author's transparency about the subjective, single-labeler bias in the underlying data and suggest future improvements like using multiple or expert labelers.

8 Show HN

Show HN: Run an 80B Qwen in 4.3 GB of RAM on a Mac, and a 35B on an iPhone

304 points · 137 comments · github.com

Swiftlet is a Swift/Metal runtime that keeps only a model's small dense core resident in memory and streams routed Mixture-of-Experts weights from SSD on demand, letting Qwen3.6-35B run in ~2.6 GB RAM (7-11 tok/s on an M5 Mac) and Qwen3-Next-80B in ~4.3 GB RAM (4.5-5 tok/s), with the 35B also running on an iPhone 17 at about 1 tok/s. It repacks experts into fixed-stride blobs so each fetch is a single SSD read, caches "hot" experts with LFU-plus-recency eviction, and runs the whole forward pass through runtime-compiled Metal shaders shared between macOS and iOS builds. The author is upfront that with only ~3B parameters active per token, the models write fluently but recall facts like much smaller models.

What the comments said

  • Several commenters point out decode speed isn't the whole story — prefill on long prompts could take a long time on this architecture, making it impractical for coding or real-time agent use but plausible for overnight background jobs.
  • A debate breaks out over SSD wear from constant expert streaming, with most concluding reads (unlike writes) don't meaningfully shorten drive lifespan, citing personal experience with old SSDs still working fine.
  • Many frame this as valuable incremental progress toward running huge models cheaply on commodity hardware, pushing back on commenters who dismiss it as impractical.
  • Some speculate this streaming approach mirrors Apple's own on-device model strategy (a small dense model in macOS that activates only 1-4B parameters per prompt), fueling discussion about whether future personal devices will run "good enough" LLMs locally instead of relying on cloud inference.
  • Users with more RAM ask about tuning cache size for speed; replies note hit rate has surprisingly little effect on throughput since Apple SSDs absorb cache misses well, though one user plans to test increasing the cache directly.

Don&#39;t stop early: Case-folding source code at memory speed

71 points · 30 comments · github.blog

GitHub engineers describe optimizing case-folding for Blackbird, GitHub&#39;s code search engine, which indexes over 180 million repositories and 480TB of source code. They found that removing an "early exit" branch that stops scanning at the first non-ASCII byte counterintuitively boosts throughput from about 3 GiB/s to over 45 GiB/s, because a fully branchless, unconditional loop lets LLVM auto-vectorize with SIMD, whereas any data-dependent early exit forces the compiler to keep the loop scalar. They released the result as an open-source Rust crate called casefold, which implements only simple 1-to-1 Unicode case folds rather than multi-character or locale-specific folds, matching the behavior of tools like ripgrep.
