3 Security

Spaghettifying DRAM

607 points · 157 comments · github.com

This GitHub project (by reverse-engineer Christopher Domas, under the xoreaxeaxeax handle) shows how to manipulate an AMD DRAM controller's undocumented but unlockable address-translation and channel/rank/bank "swizzle" registers to remap where a physical address actually lands in memory. By scrambling these low-level translations on AMD Family 16h CPUs, the technique breaks the security assumptions built on top of them — unlocking the Platform Security Processor, System Management Mode, C6-sleep-protected DRAM, and CPU microcode. The author notes newer AMD generations (17h+) simply omit this documentation publicly, and expects the underlying approach generalizes to other architectures including ARM and RISC-V.

What the comments said

  • Widespread excitement that this is presumably Christopher Domas's return, with commenters linking his earlier Defcon/Black Hat talks (MoVfuscator, sandsifter, hardware backdoors) and eagerly anticipating a talk on this work.
  • Several drew a direct comparison to the "Battering RAM" hardware DRAM-aliasing attack, calling this a software-reachable analog of that technique.
  • Some commenters were suspicious the writeup was AI-generated due to repetitive phrasing, while others argued it's simply the author's distinctive writing style.
  • A technical thread clarified scope: the exploit was demonstrated only on older AMD Family 16h chips because those are the last generation with public datasheets describing the translation registers, leaving it unclear whether newer chips are equally vulnerable.
  • A question about why DRAM "swizzling" exists at all was answered: it's a performance feature to avoid pathological access patterns hammering a single bank/channel, which incidentally provides the (now-defeated) physical-address obscurity this project exploits.

20 Computer Science

NP-overrated

203 points · 141 comments · gruhn.me

The author argues that the popular takeaway from "NP-hard" — that such problems are essentially unsolvable in practice — is a myth: worst-case intractability doesn't rule out fast solutions on the inputs that actually occur. Citing dependency resolution, type checking, scheduling, TSP, and SAT/SMT, the post notes algorithmic progress (a cited 450-billion-fold speedup from 1991–2015) and Amazon reportedly solving a billion SMT problems a day, concluding that even the canonical NP-hard problem is routinely handled at scale with ordinary engineering, not magic.

What the comments said

  • Many commenters agree with the core point: worst-case complexity classes say nothing about typical or curated inputs, and real solvers exploit structure (e.g., adding clauses to steer SAT solvers away from hard regions).
  • Several push back on the article's framing, arguing dependency managers and type systems are the way they are precisely because of NP-hardness — they deliberately restrict the problem space (e.g., dropping negative dependencies or strict version uniqueness) to stay tractable, rather than "ignoring" the theory as the post implies.
  • A notable subthread discusses the "phase transition" phenomenon in SAT, where problem hardness spikes sharply near a specific structural threshold, and how cryptography deliberately engineers into that hard region while everyday SAT instances avoid it.
  • Commenters share related folk wisdom: e.g., that TSP is effectively linear-time on many practical graph classes, and that simple O(N) vectorized passes often beat cleverer asymptotically-better algorithms in practice.
  • A few note the deeper unresolved theoretical question once approximation is allowed — the trade-off (Pareto frontier) between solution quality and computational cost — remains an active and legitimately hard research area.

How Compaction Works in Pi

158 points · 61 comments · earendil.com

This post explains how the Pi coding agent handles LLM context-window overflow via "compaction": once conversation history nears the model's context limit, Pi extracts the older messages, keeps a configurable budget of the most recent turns (~20k tokens, roughly 5-20 turns), and sends the older content to a standalone LLM request with a different system prompt ("context summarization assistant") that produces a structured handoff summary.
