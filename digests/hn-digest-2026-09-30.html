7 Formal Methods

What TLA+ can and can't check

215 points · 46 comments · buttondown.com

Responding to online hype that LLM-assisted formal verification (e.g., Claude using TLA+ to find race conditions) will solve agentic software development, Hillel Wayne lays out TLA+'s real limits: it can express invariants, action properties, and liveness properties over all possible behaviors, but can't express multi-step properties over arbitrary windows, floating point or real-time behavior, or "reachability" properties (that some behavior is merely possible). Most fundamentally, if you can't formalize a property as logic in the first place, no formal method — AI-assisted or not — can verify it.

What the comments said

  • Broad agreement that formal methods are a useful guardrail for LLM-generated designs but no substitute for actually understanding what's being built — "probabilistic guessing machines" can't escape that requirement.
  • A technical sub-thread extended the piece's limits list: TLA+ struggles to model weak-memory/non-sequentially-consistent semantics (relevant to C/C++/Rust memory models), requiring hand-rolled models of things like store buffers that aren't available as reusable libraries.
  • Several linked related prior HN discussions and essays (Tony Hoare's "How did software get so reliable without proof?", the Backus Turing lecture) situating the piece in a longer debate about formal verification's practical reach.
  • One commenter speculated that having LLMs model their own implementations in TLA+ before coding might improve output quality.
