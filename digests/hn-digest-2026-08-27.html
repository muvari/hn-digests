Saving 100 terabytes of memory by optimizing 1.1.1.1's DNS cache

873 points · 265 comments · blog.cloudflare.com

Cloudflare details five changes to how its "Big Pineapple" platform (which powers 1.1.1.1 and related DNS services) stores its 250-billion-entry DNS cache in Rust, cutting per-entry memory by over 50% and freeing roughly 100 terabytes fleet-wide. Key techniques included swapping growable Vec/String types for fixed Box<[T]>/Box<str> to drop unused capacity fields, merging separate answer/authority/additional record lists into one buffer addressed by small u16 offsets instead of full pointers, and packing boolean fields into bitflags to eliminate struct padding. The changes also improved performance, raising insert throughput 43% and cutting lookup latency 19%, showing the space savings didn't cost speed.

What the comments said

  • Some asked why such "obvious" waste wasn't caught earlier; others countered that avoiding premature optimization was reasonable until scale and rising memory costs made it worthwhile.
  • Systems programmers appreciated the low-level memory tricks and discussed inlining record data directly after the struct (flexible-array-member style), noting Rust's custom DSTs make this awkward and "half-baked" compared to C.
  • The MaraDNS author shared a first-hand anecdote of similarly optimizing blacklist storage with a single big malloc, shrinking memory from 237MB to 9.5MB.
  • A side debate questioned why the cache needs to be so large at all; others clarified it's the sum across the entire global server fleet, not one giant cache, and that DNS inherently requires caching since there's no central global record database.
  • The length-prefixed record encoding drew comparisons to TLV encoding and Linux netlink, a pattern commenters noted is common across networking protocols.

287 points · 249 comments · code.ffmpeg.org

A quickly-thrown-together ("vibecoded") fuzzing tool found a crash in FFmpeg's VPK (Sony PS2 audio) demuxer: a malformed file with a zero channel count reaches a division operation in vpk_read_packet, triggering a SIGFPE. What the comments said

Asahi Linux Progress Report: Linux 7.2

404 points · 232 comments · asahilinux.org

Asahi Linux's latest progress report details a breakthrough in Apple Silicon CPU power management: because Apple's cores lack an EL3 exception level, the kernel can't use the standard PSCI firmware interface for CPU idle states, forcing the project to rely on an out-of-tree cpuidle driver that can't be upstreamed. Developer Sven is now implementing a workaround using a UEFI Runtime Service-based PSCI conduit through the project's m1n1 bootloader/firmware layer, with kernel patches already posted upstream as an RFC. The report also covers M4-specific idle-loop bugs discovered during bring-up (where WFI causes state loss and crashes) and other hardware progress, including ACE3/SPMI support that enables USB 3.0 and Thunderbolt on M3-series devices.

What the comments said

  • Widespread admiration for the pace and depth of progress achieved by a small team reverse-engineering undocumented Apple hardware.
  • A technical aside noting va-api is a poor match for the v4l2-requests video decode API, since va-api pre-computes codec-specific data that v4l2-requests expects to parse from the raw bitstream itself.
  • Commenters pointed out the irony that Apple has quietly enabled some alternative-OS support (documented "open-os-interop" work) even while not officially endorsing or supporting installing Linux.
  • Users shared firsthand experiences with M3-series bring-up (USB3/Thunderbolt now working) and praised UTM.app's native Apple hypervisor framework (not QEMU) for fast ARM Linux virtualization on Apple Silicon.
  • Some skepticism about whether power-management tuning can realistically catch up with Apple's proprietary drivers within these devices' practical usable lifetimes, given Apple's general indifference to open-source support.
