1 AI & Society

Don't be a meat proxy

1,742 points · 704 comments · gruhn.me

The author argues against relaying raw, unread LLM output to other people in Slack, PR feedback, or chats — dubbing this behavior being a "meat proxy." Reading AI output is real work, they argue: it's verbose, jargon-dense, and often plausible-sounding nonsense, so forwarding it unread offloads that work onto the recipient. The piece extends this to code review, where pasting a ticket into an agent and relaying reviewer feedback back to it means the reviewers, not the requester, actually did the implementation. Their ask: prompt AI all you like, but read, understand, and validate before passing anything along.

What the comments said

  • Many commenters shared frustration with being handed unread AI output at work — from junior engineers to senior executives literally turning a phone around mid-generation — and called it exhausting and absurd.
  • A side debate broke out over why LLM prose has gotten terser and more jargon-dense lately, with theories ranging from models being optimized for code over prose to labs overcorrecting for past verbosity.
  • Some read the trend as evidence of broader cognitive decline or "de-evolution," invoking Wall-E-style dependency and citing claims that IQ trends are already stagnating.
  • Others described their own discipline of using AI only to research or draft internally while always writing outward-facing communication themselves, since writing is how they test whether they actually understand something.
  • A more cynical thread suggested the pragmatic response to being sent unread AI slop is simply to run it through your own LLM rather than read it either.

Prevent cognitive debt by manually retyping LLM-generated code

486 points · 400 comments · ankursethi.com

The author describes instructing their coding assistant to propose all edits in chat rather than touching files directly, then manually retyping every line into the editor themselves. They estimate this makes them only about 2x faster than not using AI at all, versus the roughly 10x some get from letting agents run free, but claim the tradeoff buys real comprehension: a mental "spatial map" of the codebase, better instincts for catching hallucinations, and the ability to refactor and clean up as they go. They frame it as the modern equivalent of old advice to type out code examples from books rather than copy-pasting them, done to avoid accruing "cognitive debt" they'll eventually have to repay.

What the comments said

  • Reactions split sharply: some called the practice a sensible middle ground for personal projects, while others mocked it as a near-religious ritual for people unwilling to fully let go of manual coding.
  • Several pushed back that this approach would make even basic UI work take days, prompting replies defending it as a deliberate speed-for-comprehension tradeoff rather than an oversight.
  • A recurring debate questioned whether most developers can actually write "better" code than current frontier models, with some insisting LLMs already beat the vast majority of programmers on common tasks and others disputing what "better" even means.
  • Many longtime programmers noted this mirrors decades-old advice to type out examples from books and tutorials rather than copy-pasting, as a way to force real understanding.
4 Programming

Bonsai: Janestreet's UI Library

357 points · 147 comments · github.com

Bonsai is Jane Street's OCaml web UI library, loosely inspired by Elm, used internally to build almost all of the firm's web apps, from the corporate directory to trading-system monitoring tools. Its core idea is separating state, incrementality, and rendering into composable primitives instead of bundling them into React-style components, so the same machinery that avoids unnecessary re-renders can also incrementalize arbitrary business-logic computations over live data. Because it's OCaml end-to-end, teams share types and logic between backend and frontend, and the library ships with a templating language, per-component stylesheets, and an expect-test framework for simulating and diffing DOM changes without a browser.

What the comments said

  • Commenters clarified that despite looking web-only, Bonsai also has a full terminal UI implementation that at least one engineer uses for personal tools like a contacts database.
  • A technical thread explained why Bonsai needs a userland trampoline: js_of_ocaml lacks general tail-call optimization since most browsers besides Safari don't support it natively.
  • Several commenters ribbed the "Why Bonsai?" pitch as quintessential Jane Street — building everything from HardCaml to web frameworks in-house purely out of enthusiasm for OCaml — and compared it to similar backend-to-frontend efforts like Ocsigen/Eliom, ScalaJS, and F#'s Fable.
  • A broader tangent questioned whether bespoke UI frameworks matter anymore at all, given some commenters believe AI agents can now generate custom, dependency-free UI code on demand.
5 Open Source

Devtools must be open source

611 points · 205 comments · blog.exe.dev

The author argues coding agents have changed the economics of customizing software: an agent can be told to fetch a tool's source, modify it, and then a scheduled prompt can continually rebase those local changes onto upstream releases, making the old open-source promise of "freedom to modify your tools" practical for ordinary users rather than just experts with spare time. They walk through building "meat," a tool that uses an LLM to strip boilerplate out of diffs before code review, directly into their own agent-driven editor (Shelley) with a single prompt. What the comments said

  • A major thread pushed back hard, worrying that agent-modified software (bank apps, internal tools) creates unowned risk — subtle bugs or vulnerabilities with a "userbase of one" to catch them, and no clear answer for who's responsible when it breaks.
  • Others disputed the implied end of config files and settings UIs, arguing it's wasteful for every user's agent to re-derive the same options dialog rather than building it once centrally.
  • Some accused the "personalization" framing of being a coordinated marketing narrative that had been circulating that week, and noted the author's company has a commercial stake in the pitch.
  • Commenters shared mixed real-world experience: several reported maintainers rejecting AI-attributed patches upstream, leaving them stuck maintaining private forks anyway, while others described genuine success using agents to quickly clone and understand unfamiliar codebases.
6 AI & ML

LLMs reward expertise

961 points · 408 comments · seangoedecke.com

The author argues that despite LLMs turning everyone into a passable generalist, real skill in prompting still comes down to domain expertise, illustrated by Terence Tao's conversation with ChatGPT about a counterexample to the Jacobian Conjecture — Tao's terse, expert-level pushback produced far more sophisticated results than an amateur could extract from the same model. The author draws a parallel to their own work with codebases: familiarity with a system lets you push an LLM harder ("no, I think it could be simpler here") instead of accepting whatever it proposes first. The piece concludes that human expertise remains the bottleneck, since the hard part is communicating exactly what solution you want, not pulling information out of the model.

What the comments said

  • Many commenters agreed, offering their own analogies — acting as a "team lead" directing a junior-dev LLM, or needing the exact right keyword to unlock relevant knowledge the model otherwise withholds.
  • Some pushed back by pointing to a leaked prompt from Anthropic's own math researcher that was vague and hype-y rather than expert, arguing this undercuts the expertise thesis; others countered that math is uniquely self-verifiable via proof-checking, so the pattern may not generalize to less verifiable domains.
  • A competing technique got equal support: unstructured "brain dump" rambling into speech-to-text works well for many, since the model won't be offended by disorganization as long as the key facts eventually surface.
  • Disagreement over whether LLMs simply amplify existing ability ("more ability, more impact") or amplify ineptitude and chaos just as readily.
  • A few blamed management pressure and hype ("Claude, make me Microsoft Flight Simulator, make no mistakes") for pushing engineers toward exactly the shallow, non-expert prompting the article warns against.

16 Programming

Rust project goals: Immobile types and guaranteed destructors

235 points · 99 comments · github.com

This is an official Rust project goal proposing new opt-out traits — Move, Forget, and Destruct — that make "can this type be relocated" and "can this type be forgotten without running its destructor" explicit properties of types rather than implicit assumptions baked into the language. It would let self-referential async types be immovable without the complexity of Pin, and let types like transaction handles or scoped task handles guarantee their destructors run, unblocking patterns like safe scoped async spawn. The plan spans 2026–2027: a compiler MVP, RFCs, and real-world validation inside the Linux kernel, while explicitly leaving changes to the Future trait itself out of scope.

What the comments said

  • Several commenters ask what this actually unlocks in practice; the consensus answer is structured/scoped concurrency for async — letting spawned tasks safely borrow from a parent's stack the way scoped threads already can.
  • One thread frames the proposal as "more algebraic effects retrofitted onto Rust," which others push back on, arguing it's a type-level capability rather than a function-level effect.
  • A recurring technical concern: mem::forget isn't the only leak vector (reference cycles via Rc/Arc can leak too), and commenters discuss how the Forget bound would need to auto-propagate through generics, with smart pointers requiring their pointee to be Forget.
  • Many are enthusiastic that immovable types are finally getting a real solution after years of assuming it was infeasible without breaking the ecosystem, though some worry a !Move/Pin split could fragment existing code.
  • Others note this competes with a separate "pinned places" proposal (place-based rather than type-based immovability) and draw comparisons to OxCaml's approach to the same problem.
