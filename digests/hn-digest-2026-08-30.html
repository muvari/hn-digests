1 AI & Infrastructure

Creepy Crawlies

1,293 points · 637 comments · people.kernel.org

Kernel.org maintainer Konstantin Ryabitsev quantifies how badly AI scraper bots are hammering git.kernel.org, finding that rendering commits to HTML for crawlers now consumes more CPU than all legitimate traffic combined, including git clones. He describes an escalating arms race: blocking by user-agent, then IP, then ASN, and finally deploying the Anubis proof-of-work challenge system — which bots have since learned to solve at increasing difficulty levels by routing through residential and mobile IP botnets ("proxy SDK monetization"). The post ends without resolution, framing this as an ongoing, unsolved war of attrition.

What the comments said

  • Commenters note the irony that crawling for "AI" training data is done via the least AI-efficient method possible — rendering each commit as HTML instead of just git clone-ing the repos directly.
  • Some argue this isn't really a contradiction: scrapers are generic, unintelligent pipelines (often themselves vibe-coded), not the LLMs they feed, so there's no reason to expect them to special-case efficient data sources.
  • Several suggest caching/reverse-proxy fixes, though others point out the cache is constantly evicted because scrapers deliberately hit the long tail of old commits.
  • A few floated adaptive Anubis difficulty scaling with request rate, but others note this fails against botnets that only make a handful of requests per IP before rotating.
  • Broader discussion ties the flood to "proxy SDK monetization" — apps and even smart TVs secretly reselling residential IP addresses to scraping operations.

3 Security

Arbitrary code execution in QubesOS via copy-to-VM error reporting backchannel

244 points · 96 comments · qubes-os.org

Qubes OS disclosed QSB-118, a vulnerability in dom0's qvm-copy-to-vm tool: when copying a file from dom0 to a compromised qube, the target qube can return a malicious filename in its error report. That filename is only partially sanitized before being passed to system() to launch an error dialog, letting a compromised VM inject arbitrary shell commands that execute with full dom0 privileges. The VM-side equivalent isn't affected since it avoids system(). A patched package (4.3.22) is available.

What the comments said

  • Commenters call out system() as fundamentally unsafe for privileged code and criticize checking for a binary via full path but then relying on $PATH resolution to actually run it.
  • Several note the practical exposure is limited since best practice already discourages copying files into dom0, but that Qubes's threat model exists precisely to protect less technical users who don't follow best practices.
  • Commenters commend the transparency and rigor of the disclosure, including detailed instructions for authenticating the signing key out-of-band.
  • A tangent debates whether GPU passthrough could ever be safely added to Qubes, given how large a driver attack surface that would introduce into dom0.

14 Security

Omarchy: Any User Process Can Escalate to Root

507 points · 506 comments · 0xcc.io

A security researcher found that Omarchy, DHH's Arch Linux-based desktop distribution, added every default user to the docker group — which, because the Docker daemon runs as root and listens on a socket that group members can access, effectively grants root to any process in the user's session, including browsers, editors, and AI coding agents, without a password or sudo prompt. The issue was privately disclosed and fixed in version 4.0.1; the researcher recommends switching to rootless Podman instead.

What the comments said

  • Many commenters are baffled that Docker, rather than rootless Podman, was ever the default, calling it a well-known footgun that a security-focused distro should have avoided from the start.
  • Several note the misconfiguration is common enough that LLM coding agents have reportedly exploited it unprompted just to complete assigned tasks.
  • Some argue the practical risk is overstated for a single-user desktop, since an attacker with home-directory access already has plenty of avenues to escalate; others counter that root access still meaningfully raises the ceiling of what a compromise can do.
  • The documentation itself is criticized as actively misleading — describing the setup as letting users "run Docker... not as root," when it actually grants root-equivalent access via group membership.
  • The author credits Omarchy's fast response but says a pattern of prior security issues has eroded their trust in the project's decision-making process.

21 Programming

Zig: Pointer Stability for ArrayLists

113 points · 75 comments · ziglang.org

Zig's standard library extends the "pointer stability lock" pattern, previously added to HashMap, to std.ArrayList. Code that stores a pointer or slice into an ArrayList's backing memory can now call lockPointers()/unlockPointers() around that usage; if the list is resized while locked — which could silently invalidate those pointers and cause memory corruption — it now panics immediately with a stack trace instead of producing a subtle, hard-to-diagnose bug.

What the comments said

  • The top comment questions whether ArrayList is even the right structure when stable pointers are needed, suggesting storing indices instead, sparking nostalgia for Zig's since-removed SegmentedList.
  • A detailed critique argues the mechanism is weak compared to Rust's compile-time borrow checking: it's opt-in, easy to forget, and the lock scope isn't statically tied to the function that needs it.
  • Others defend the tradeoff as consistent with Zig's philosophy — prioritizing low-level control and explicitness over Rust-style guarantees, in exchange for less abstraction overhead.
  • A technical side-thread clarifies debug allocators can't catch this class of bug because it's not a use-after-free issue — the memory is still valid, it's just moved, which requires structural tracking rather than allocator-level instrumentation.
  • Also noted: the check only fires in Debug/ReleaseSafe builds, not ReleaseFast, since it adds overhead to a hot path.
