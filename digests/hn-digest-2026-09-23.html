697 points · 713 comments · anthropic.com

7 Hardware

ReBarUEFI: Resizable BAR for almost any UEFI system

237 points · 76 comments · github.com

ReBarUEFI is an open-source UEFI DXE driver that adds Resizable BAR (ReBAR) support to motherboards whose firmware doesn't officially support it, by patching the firmware's PCI resource-allocation code. Resizable BAR lets the CPU address a GPU's full VRAM instead of the traditional 256MB-chunk limit, typically yielding a 5–15% gaming performance boost, and is required for Intel Arc GPUs to work optimally; the project also bundles patches for related firmware bugs (BAR size limits, MMIO space limits, USB3 conflicts) on older Intel and AMD platforms.

What the comments said

  • The top comment thread was people asking what ReBAR actually is and does, answered by others explaining the CPU-to-VRAM addressing limitation it solves.
  • Several shared personal stories of hand-patching BIOS on old workstation boards (X79, X99) to get modern GPUs or NVMe boot working before tools like this existed.
  • One user is looking for the inverse — patching a GPU's own firmware (an RTX 3080 20GB card) to add ReBAR support — and was pointed to a companion project, NvStrapsReBar.
  • A tangent touched on Coreboot as a more thorough (but more limited-hardware-support) alternative to ad hoc firmware patching, with a suggestion that AI tools could now make analyzing proprietary BIOS blobs more tractable.

VSCode's SSH Agent Is Bananas (2025)

259 points · 161 comments · fly.io

Fly.io's Thomas Ptacek describes how VS Code's Remote-SSH extension works: rather than living off the land like Emacs's Tramp (which just runs shell commands over an existing SSH session), it stages and installs a full agent binary — including a bundled Node.js runtime — on the remote host, which then opens a WebSocket back to the local VS Code client that can browse the filesystem, edit files, spawn PTYs, and persist itself. What the comments said

  • A side-thread compared it to Emacs Tramp (bare shell, no binary install, works everywhere but slower) versus newer tools like tramp-rpc that trade purity for speed, in the same spirit as VS Code's approach.
  • Multiple commenters noted this is standard practice among remote-dev tools (JetBrains does the same), and that the underlying complaint is really about running it against machines you shouldn't trust it with.

21 Security

Data-only attacks are easier than you think (2024)

100 points · 43 comments · usenix.org

This USENIX ;login: piece explains "data-only attacks" — exploits that corrupt a program's data (like a config variable or file path) rather than its control flow, letting the program's own legitimate code carry out malicious actions using attacker-supplied values. Using a toy example (overwriting a web server's CGI-BIN path variable to redirect execution to /bin/sh), the authors show these attacks bypass modern control-flow defenses like DEP, CFI, and CPI since no code pointers are hijacked, and present their tool Einstein, which automatically generates such attacks, arguing they're far easier to build at scale than previously assumed.

What the comments said

  • Several security-minded commenters clarified the key distinction from ordinary memory-safety bugs: the attacker still needs an initial memory-corruption primitive, like a buffer overflow, but uses it only to alter benign data values rather than to redirect execution or inject code.
  • One noted this shows why control-flow-only defenses are fundamentally incomplete, since a data-only attack never diverts execution to attacker-chosen instructions.
  • A tangent connected the piece to taint analysis as an underused technique for finding this class of vulnerability, with pushback on the terminology and a note that taint tracking can't stop the underlying corrupting write itself.
  • Others broadened the discussion to "logic" vulnerabilities generally, like e-commerce refund fraud, arguing these are in some ways an even harder version of the same "correct code, malicious data" problem.

No Easy Fix for Bogus Respondents in Online Opt-In Polls

56 points · 36 comments · pewresearch.org

A Pew Research study tested three methods for screening "bogus" — fraudulent or careless — respondents out of online opt-in surveys: attention-check "trap questions," a commercial prescreening service, and matching respondents to a voter file, and found no method fully solves the problem. Voter-file matching actually increased error by disproportionately removing legitimate respondents who simply declined to share identifying information, while trap questions and prescreening performed similarly, offering modest data-quality improvements; all three approaches slightly increased overestimates of Democratic support in the 2024 election because bogus respondents tended to claim they'd voted for the eventual winner regardless of their actual behavior.

What the comments said

  • Several commenters argued the "easy fix" is simply not to do online opt-in polling, though others countered that phone and offline random-sample polling have their own severe demographic skew and coverage problems.
  • A thread of historical online poll manipulation examples — 4chan's Time Person of the Year and Kim Jong-un stunts, Boaty McBoatface — was offered as evidence this problem long predates AI-generated bogus responses.
  • One striking detail people picked up on: roughly 10% of respondents falsely claimed to have visited the International Space Station, illustrating how many respondents answer carelessly or dishonestly.
