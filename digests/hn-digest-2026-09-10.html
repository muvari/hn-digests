1 Mobile Dev

Shopify is moving from React Native back to Swift and Kotlin

1,132 points · 831 comments · shopify.engineering

Shopify announced it's abandoning React Native in favor of native Swift/Kotlin development across its major apps (Shopify, Shop, POS, Inbox), reversing the 2020 decision that made RN central to its mobile strategy. The company says coding agents have become capable enough to implement, translate, and review code across both platforms that the original cost savings of "write once" no longer outweigh native's UX and performance advantages. They're doing a "greenfield" rewrite rather than gradual migration, and are addressing the future of open-source libraries they maintain (React Native Skia will be forked by its maintainer, FlashList seeks new stewardship, Restyle will be archived).

What the comments said

  • Many commenters see this as a leading indicator: LLM coding agents are shifting the cost-benefit calculus that justified cross-platform frameworks industry-wide, with some predicting a broader swing back to native.
  • Skeptics pushed back that React Native's performance penalty was always the real tradeoff, not fashion, and that agents just changed the economics rather than proving RN was a mistake.
  • Some questioned the token/compute cost of maintaining two native codebases via AI, and whether agents can really handle cross-platform architecture decisions unsupervised.
  • Others noted React Native still forces developers to drop into native code for anything performance-sensitive, making the "native anyway" argument a longstanding complaint.
  • A few joked about the "wheel of fashion" cycling technology choices, while others predicted Flutter faces the same fate.

701 points · 459 comments · rustfoundation.org

Neki – Sharded Postgres

255 points · 134 comments · planetscale.com

PlanetScale launched Neki, a sharded Postgres platform now in preview, built on lessons from running large sharded MySQL clusters. Applications connect through a Neki router speaking the standard Postgres wire protocol, while each shard is a real, unmodified Postgres cluster with a primary and replicas across availability zones — avoiding the compatibility and extension losses common to other distributed-Postgres approaches. A JSON "data topology" defines shard keys and groupings, and schema changes, failovers, and resharding all run as built-in online workflows.

What the comments said

  • The single most common complaint: the launch post buries what Neki actually is under paragraphs of "why" and "how" before ever clearly stating the product, forcing readers to the separate neki.dev marketing site for a plain explanation (which PlanetScale reportedly patched in response).
  • Commenters flagged the lack of any discussion of cross-shard consistency guarantees, guessing eventual consistency with replica lag given zero mentions of "consistency" in the post.
  • Several noted cross-shard transactions and foreign keys aren't yet supported ("coming soon"), meaning today it functions more like several independent Postgres clusters than a unified distributed database.
  • Whether Neki will be open-sourced is undecided, according to a PlanetScale employee response in the thread.
  • Some were intrigued by the sidecar-based connection pooling, which claims to beat a plain PgBouncer setup by sizing pools based on real visibility into both the router and Postgres sides of each connection.

JEP 544: Ahead-of-Time Code Compilation

98 points · 42 comments · openjdk.org

This OpenJDK proposal (part of Project Leyden) describes compiling application code to native code ahead-of-time during a training run and caching it, so the HotSpot JVM can load already-optimized native code at startup instead of relying purely on interpretation and JIT warmup. If the production workload diverges from the training run, HotSpot can still dynamically deoptimize and recompile as needed, aiming to combine AOT's fast startup with JIT's ability to adapt to changing hot spots — targeting AArch64 and x64 without requiring any application code changes.

What the comments said

  • Commenters compared this favorably to prior AOT efforts like Excelsior JET, IBM J9, and GCJ, several lamenting that Sun/Oracle never invested in similar native-compilation approaches decades earlier when it might have helped Java on the desktop.
  • Some pushed back on the JEP's non-goal of full cross-architecture and CPU-support parity, seeing it as evidence the JVM's traditional "write once, run anywhere" portability promise is being deprioritized in favor of raw performance.
  • A dev running a code-execution sandbox for a coding-challenge site shared concrete numbers: Java's ~2.5-3s startup (mostly javac + JVM boot) forced a stricter rate limit than Go (~1.7s) or Swift, and hoped this JEP could cut that to a few hundred milliseconds.
  • Several found the required "training run" step to be a real practical burden, since tooling for generating and integrating these training runs into build pipelines is still immature compared to Android's ART or OpenJ9's more automatic JIT caching.
  • One commenter clarified this doesn't replace JIT compilation — it caches previously JIT-compiled code so it's available immediately at startup, with the JIT still free to discard and regenerate it later.
