Show HN: Wyzer Programming Language

197 points · 107 comments · github.com

Wyzer is a new statically-typed, compiled language that combines a Perceus-based reference-counting memory model (borrowed from Koka and Lean 4) with choreographic programming, applying one ownership rule to memory, threads/interrupts, and distributed network communication in an attempt to rule out memory bugs, deadlocks, and protocol mismatches at compile time. The pitch is Rust-level safety without Rust's learning curve, generating matched send/receive code from a single choreography description rather than writing and hoping each side of a network protocol agrees. The project is early-stage, and by the creator's own admission the docs don't yet fully explain its most novel ideas.

What the comments said

  • Many noted the syntax closely resembles Rust and generally welcomed that it looks conventional (like C/TypeScript/Java) rather than exotic.

  • The deepest thread dug into how choreographic programming prevents distributed deadlocks: a commenter identifying as a researcher in the field explained that a choreography expresses a send/receive pair as one atomic instruction that gets "projected" into per-participant code, so mismatched protocols can't be written at all, at the cost of only supporting communication patterns the choreography language allows.
  • Commenters were surprised to learn from a linked post that the creator started the project at age 8 and is now 14, prompting a mix of admiration and some unease.
  • The creator engaged directly throughout the thread, saying documentation is being written without AI assistance and pointing to a "donut.wyz" demo (a Wyzer port of the classic spinning-donut program) as a worked example.

17 Performance

Assembly Hall of Shame

330 points · 83 comments · github.com

This repo is a tongue-in-cheek leaderboard that ranks x86 instructions not by speed but by how many cycles a single instance can be made to burn, using deliberately adversarial setups (denormals, MMIO contention, cache/TLB abuse) rather than normal profiling. The reigning "champion" abuses fxrstor64 to load FPU state from a high-latency PCIe MMIO region while other cores hammer a different MMIO address to saturate the bus, stalling one instruction for roughly 198 billion cycles (about 62 seconds). Lower-ranked entries range from a plain nop (1 cycle) up through pathological cases like idiv, fsin, mfence, and mov cr3, each documented with the specific microarchitectural trick used to slow it down.

What the comments said

Radical Study Suggests Life on Earth Arose Twice

138 points · 97 comments · sciencealert.com
