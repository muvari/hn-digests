Linux 7.3 improves performance when running out of vRAM

523 points · 296 comments · pixelcluster.dev

A kernel developer explains newly-merged Linux 7.3 patches that improve how the system handles VRAM overcommit in games, i.e., when a game requests more GPU memory than is physically available. The post digs into why evicting memory to slower CPU RAM (accessed over PCIe) doesn't have to be catastrophic, showing via microbenchmarks that cache-friendly or infrequently-accessed allocations suffer far less from eviction than naive expectations suggest, and that smarter eviction policies can keep performance closer to acceptable even under VRAM pressure.

What the comments said

  • Commenters broadly praised the writeup as clear, technically deep, and a good example of enthusiast-driven kernel work.
  • A technical side-discussion focused on display scanout buffers, which must use physical (non-virtualized) memory; commenters noted a small 32MiB scanout image could trigger up to 4GiB of evictions, and questioned why that memory isn't simply reserved to avoid the cascade.
  • Several asked whether this matters for compute/LLM inference rather than gaming; the consensus was it likely doesn't help much there, since inference workloads are more predictable and already manually managed, and are bottlenecked by data movement rather than compute.
  • A tangent on GPU-to-NVMe swapping suggested it would be roughly 4x slower than PCIe-to-RAM in the best case given typical NVMe lane counts.
  • Some commenters used the post to jab at Windows update culture, contrasting it with excitement for the next Linux kernel release, though others pushed back that some recent Windows Insider updates have also been well received.

  • A major discussion thread centers on the finding that rationed children also ate less sugar as adults, with commenters debating whether the cancer/aging effects stem from early biological programming, lifelong lower sugar intake, or simply eating less overall (calorie restriction) rather than the early-life window itself.
  • The obligatory 'correlation isn't causation' comment appears and gets pushback from others noting this is a quasi-experimental design specifically built to approximate causal inference, not a simple correlational study.

The article itself could not be retrieved (it returned an HTTP 403 error both on direct fetch and via WebFetch), so this summary is drawn from the title and HN discussion. What the comments said

  • Several point out the hardware context driving DOS 2.0: supporting the PC XT's new ST-506/ST-412 'Winchester' hard disks required directory structures absent from DOS 1.x.
  • A tangent covers DOS's SWITCHAR option, which let users swap the Unix-style '/' for '-' as an option character, and was dropped because third-party programs handled it inconsistently; several lament the backslash path separator as a lasting annoyance.
  • Overall the thread is appreciative and nostalgic, with people who did 8086 assembly or Xenix/DOS systems work in that era calling the piece (or at least its subject matter) enlightening.

The Benchmarkpocalypse

What the comments said

How do functions like alloca allocate memory from the stack?

67 points · 66 comments · devblogs.microsoft.com

Raymond Chen explains how functions like _alloca() dynamically allocate stack memory on Windows/x86-64 by calling the same __chkstk() helper used to probe large fixed-size stack frames past the guard page.
