16 AI & ML

Dust: Pretraining Transformers Without Backpropagation

237 points · 62 comments · qlabs.sh

Researchers present Dust, a zeroth-order (gradient-free) method for pretraining transformer language models that perturbs activations per-token rather than weights, letting one forward pass effectively evaluate an entire "virtual population" in parallel. The paper reports that Dust is orders of magnitude more compute-efficient than prior evolution-strategies approaches, that larger models become more population-efficient (counter to conventional wisdom about zeroth-order methods not scaling), and that its gradient estimates track backprop's increasingly closely as population size grows, with no observed plateau up to 1B tokens of testing.

What the comments said

  • Commenters debated whether this is mainly a parallelism win rather than a compute-efficiency win, since backprop itself already parallelizes well via matrix multiplication; some pointed to related asynchronous techniques like predictive coding as the real draw for exotic hardware.
  • The standout empirical result people flagged was a 243M-parameter model being more population-efficient than one 120x smaller, which several found genuinely surprising given prior assumptions about zeroth-order scaling.
  • A skeptical take dismissed the approach as "yawn-worthy" Monte Carlo gradient estimation dressed up as novel, comparing it to other technically-interesting-but-impractical techniques like homomorphic encryption or blockchain computing.
  • Others were more optimistic that a hybrid approach — fine-tuning an already-backprop-trained checkpoint with Dust — could be a promising next experiment.

Ephemeral Testing

71 points · 26 comments · lemire.me

Daniel Lemire proposes "ephemeral testing": instead of evaluating a library or component directly, have an AI agent build a throwaway application or extra layer on top of it, then judge the quality of that generated code as an integration test of the underlying component. A clean API with stable invariants and good error messages lets an agent build something functional quickly; messy, hidden-state, or poorly documented libraries make the agent (and the resulting throwaway code) struggle, surfacing design flaws indirectly.

What the comments said
