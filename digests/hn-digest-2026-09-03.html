14 Web Performance

The browser's main thread is expensive

408 points · 142 comments · kciter.so

The post explains why the browser's single main thread — which handles both JavaScript execution and most of the rendering pipeline (style, layout, paint) — is behind most perceived "jank": a long-running JS task blocks rendering and input handling because everything queues on the same thread, and against a roughly 10ms-per-frame budget at 60Hz, even brief blocking is costly (metrics like INP and TBT both essentially measure main-thread blocking). It lays out two remedies: spend main-thread time more deliberately (splitting, batching, prioritizing, deferring) or move work off it entirely (compositor-only CSS animation, web workers, OffscreenCanvas).

What the comments said

  • Widely praised for clear writing and interactive demos contrasting JS-thread animation (freezes when blocked) with compositor-driven CSS animation (keeps running regardless).
  • Some argued most sites don't need to worry about this if they avoid unnecessary complexity, while others noted it's genuinely useful for anyone building interactive, animation-heavy, or real-time apps.
  • Practitioners shared adjacent techniques: transferControlToOffscreen() for canvas rendering in a worker beat manually transferring ArrayBuffers, and a reminder that ArrayBuffers copy by default unless explicitly marked transferable.
  • A few wished JavaScript's await could yield conditionally rather than requiring manual shouldYield()-style workarounds.
