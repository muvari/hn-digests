In an $80 motel room, a discovery to shed light on the origins of life

282 points · 108 comments · nytimes.com

Evolutionary biologist Julia Van Etten turned an $80 motel room in Nags Head, North Carolina into a makeshift field lab, filling it with jugs of brackish marsh water and using bedside tables as microscope stands to scour samples for swamp algae. Don't couple your Go code to GitHub

302 points · 157 comments · iain.rocks

Because Go import paths double as fetch locations, hardcoding a package's source as e.g. github.com/user/repo permanently couples that code to GitHub; the author cites a real company that ended up paying for three separate git hosting providers simultaneously because migrating away from stale import paths was too costly to undertake. His proposed fix is to use a custom "vanity" domain (like go.iain.rocks) with a go-import meta tag that redirects to wherever the code actually lives, so the underlying git host can be swapped without breaking anyone's imports. He shares his nginx config and HTML snippet so others can replicate the setup.

What the comments said

  • Many pointed out the tradeoff just moves the coupling problem: a personal or company domain can lapse or go unpaid far more easily than GitHub disappearing, especially for solo open-source maintainers.
  • Several argued the underlying issue isn't Go-specific — hardcoded GitHub links anywhere (comments, docs) rot after a migration — while others countered that such links are a trivial search-and-replace fix.
  • A side debate questioned whether a URL is even the right abstraction, floating URNs or content-addressed identifiers with multiple resolvers as more "correct" alternatives.
  • Commenters pushed back on trusting GitHub as permanent too, noting companies do delete or unpublish old repos (to shed support or security-liability burden), reinforcing general advice to vendor dependencies regardless of hosting choice.

10 Rust & Performance

The state of SIMD in Rust in 2026

190 points · 47 comments · shnatsel.github.io

Written by a maintainer of the Fearless SIMD library, this annual survey covers the three ways to get SIMD in Rust — automatic vectorization, portable SIMD abstraction libraries, and raw platform-specific intrinsics — and explains why cross-platform SIMD is hard: x86 fragmented its SIMD extensions over decades (SSE2 through AVX-512) requiring runtime feature detection and function multiversioning, while ARM made NEON a mandatory baseline on all 64-bit chips. It also highlights that Rust 1.98's newly stabilized "algebraic" floating-point operations finally unblock auto-vectorization of float code that previously couldn't be safely reordered, and surveys the current library ecosystem (std::simd, wide, pulp, macerator) plus multiversioning tooling.

What the comments said

  • A central debate formed around whether "portable SIMD" is a myth — some argued real performance requires hand-written per-platform intrinsics and portable libraries really just deliver "portable auto-vectorization," while others countered that a reliable 2–4x from a portable library beats a theoretical 8x from hand-tuned code that in practice never gets written.
  • Commenters shared experience reports of maintaining their own SIMD abstraction libraries (currently x86-only) with plans to migrate to core::simd once it stabilizes.
  • Several noted a documentation gap between platforms: ARM chip vendors publish far less low-level ISA and performance documentation than Intel, making it harder to know which intrinsics require which feature flags.
  • There was discussion of real-world baseline assumptions — games and Linux distros increasingly just require modern hardware (or ship multiple architecture-level builds) rather than support very old CPUs, and Windows 11's AVX2 requirement effectively guarantees a usable baseline for many applications.
  • One commenter noted that SIMD codegen support in Cranelift remains limited and work-in-progress compared to LLVM.

12 Programming

Writing Efficient C++ Code (2013)

170 points · 137 comments · asawicki.info

This 2013 article (originally published in a Polish programming magazine) argues that writing genuinely fast C++ requires thinking about data layout before algorithms, a philosophy it calls Data-Oriented Design. It contrasts scattered, pointer-linked small objects (common in classic OOP) with contiguous array-based layouts, arguing the former causes both frequent cache misses when traversing memory and difficulty parallelizing code because you cannot safely reason about what a virtual method touches. The piece positions this not as abandoning classes and OOP conveniences, but as staying closer to the hardware when performance is a hard requirement, such as in games, real-time media, or resource-constrained devices.

What the comments said

  • A recurring disagreement with the submission's framing: several commenters push back on the idea that modern C++ has made efficient low-level code harder to write, arguing that features like C++23 move semantics and constexpr have actually made it easier to get the compiler to generate good code.
  • Commenters diverge sharply on how often performance tuning actually matters day to day: some say straightforward C++ is already "blazingly fast" for their work, while others counter that whole domains (robotics, HFT, telecom, embedded) treat every CPU cycle, watt, and byte as a zero-sum resource.
  • Multiple people expand on the article's data-oriented-design points with concrete numbers, describing large measured speedups from switching polymorphic pointer collections to std::variant and then to structure-of-arrays layouts, while noting the gains are more workload-dependent (e.g., less relevant when rendering dwarfs simulation cost in games).
  • Some readers criticize the article itself as too shallow for the subject, pointing out it barely touches branch prediction, context switching, or synchronization, and suggest the topic deserves a book or series rather than a single post; others share supplementary references like Agner Fog's optimization manuals.
  • A "premature optimization" camp argues most teams should focus on avoiding accidental algorithmic complexity first, while a counter-anecdote (std::map beating vector until around nine elements in one benchmark) is offered as a caution to always measure on real data rather than trust rules of thumb.

Imp is a full port of DSPy to the BEAM

93 points · 9 comments · github.com

Imp is an Elixir library that ports Stanford's DSPy framework to the BEAM virtual machine, letting developers declare typed "signatures" for language-model calls (what a step takes in and returns) instead of hand-writing prompts, then wrap those signatures in modules like chain-of-thought reasoning or tool-using ReAct-style agents. Given labeled training examples and a scoring metric, Imp's optimizers (including GEPA, which uses a stronger model to read failures and rewrite instructions, plus MIPROv2, BootstrapFewShot, and fine-tuning options) automatically improve a program's prompts and can save the results as a reviewable diff. Because it runs on OTP, each agent executes as its own supervised process with built-in state, concurrency, and authorization hooks that can restrict which tools a running agent is allowed to call.

What the comments said
