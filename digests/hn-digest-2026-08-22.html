2 Programming

Rust Glancer: Rust LSP using 100x less RAM

409 points · 104 comments · rust-glancer.github.io

Rust Glancer is a new alternative to rust-analyzer built around a "frozen analysis" model instead of an incremental in-memory one: it indexes a workspace once, writes the results to disk, and loads only what's needed per query, targeting under 100MB of RAM even on old hardware. The tradeoff is that saves — not keystrokes — trigger reindexing, so newly typed imports/structs aren't visible until the file is saved, though shallow per-keystroke analysis keeps completions responsive. After four months of solo work it already supports goto-definition, hover, inlay hints, and completions for most "normal" Rust, though it's far from feature-complete.

What the comments said

  • The author showed up to answer questions directly, clarifying design tradeoffs (e.g., why the incremental rust-analyzer approach uses more memory than the offload-to-disk approach) and fielding requests for Zed support.
  • Commenters who work with agentic coding tools were enthusiastic, noting rust-analyzer's memory footprint is especially painful when agents make lots of out-of-editor edits; Rust Glancer's design explicitly deprioritizes reindexing from agent-driven changes.
  • A tangent broke out about jargon: some found "LSP" unexplained and confusing, while others argued Language Server Protocol is now common-knowledge terminology for this audience.
  • Several asked how it compares to JetBrains' Rust Rover, which also uses a different (non rust-analyzer) architecture, but no one had a rigorous comparison yet.
  • One reply thread noted the linked matklad blog post covering the same project was written by a different person than the popular Rust blogger of the same-sounding name, a mix-up dang corrected in the thread.
3 AI & Software

There's no reason for software to be slow anymore

626 points · 481 comments · danluu.com

Dan Luu argues that LLM agents have collapsed the cost of performance engineering that used to require rare, specialized expertise — building JIT compilers, custom text indexes, or hand-tuned regex engines used to be too expensive to justify for all but the largest projects, but now anyone who can "type a few sentences" can direct an agent to do it. He illustrates with FRE, a regex engine his agent built and tuned over a month against benchmarks, and a follow-up experiment where an agent added ahead-of-time native compilation to speed up long ripgrep queries in the background, yielding a modest but real ~7% speedup on representative workloads for minutes of human effort.

What the comments said

  • Many pushed back on the premise, arguing user-facing software feels slower than ever, not faster — attributing this to incentives (features that "close sales" beat invisible performance work) that AI compresses timelines for but doesn't redirect.
  • Several commenters said the post's own site was hard to read without browser Reader Mode, criticizing dense self-referential linking as ironic given the "no reason to be slow" thesis.
  • Some raised the counterpoint that unbounded token/compute spend to optimize code has its own real dollar and environmental cost, and that teams will eventually have to budget "token spend" much like they used to budget developer time.
  • Others noted a tension between speed and extensibility/customization: hyper-optimized, pre-baked code (e.g. SIMD regex) is inherently less flexible than general-purpose, slower-but-adaptable designs.
  • A few commenters simply noted that most users, weighted by the revenue they generate, don't actually care about speed — so market incentives won't necessarily shift even if the technical cost of fixing it has dropped.

  • People shared personal nostalgia about cutting their teeth writing Z80 assembly on the ZX Spectrum, and some still tinker with CP/M emulation today as a low-abstraction break from LLM-heavy workflows.
  • A side thread on transistor counts noted the original 8080 had ~4,800 transistors versus roughly 100 billion in an Apple M5 Max, sparking debate over what's a fair comparison point (whole vintage systems vs. modern SoCs).

10 Observability

OTel isn't going well

224 points · 114 comments · matduggan.com

The author digs into the long-standing feeling that OpenTelemetry perpetually feels unfinished, concluding it's not simply an underfunded-open-source problem but a structural "three-way crash": a strict stability gate, a small maintainer bench, and a massive multi-language scope combine to make maintainers reluctant to ever mark anything stable, since stable APIs can't change. The piece traces the actual workflow for shipping a change (OTEP proposal → specification → semantic conventions → per-language SDK implementation → contrib/collector), showing how the split between tightly-reviewed "core" and looser "contrib" packages creates friction, especially around the collector, where users often must build their own custom binary via the OpenTelemetry Collector Builder.

What the comments said

  • Several commenters vented specific frustrations: heavy performance overhead (especially painful for serverless cold starts), needing both gateway and edge collectors for realistic deployments, and vendors still shipping only alpha/beta OTel support despite years of the project existing.
  • Defenders argued the alternative is worse — proprietary vendor lock-in — and that OTel's real value is a shared wire protocol (OTLP) that lets any source work with any sink, even if the surrounding tooling is rough.
  • One detailed rebuttal argued OTel conflates two things that used to be handled well separately and simply (Prometheus for metrics, Jaeger for tracing), and that its complexity stems from trying to unify concerns that don't need unifying.
  • A popular request was for tracing, metrics, and logs to be unified enough that you could annotate code once and dynamically choose after the fact whether to expose something as a metric, log, or trace — something OTel's separate-spec-per-signal approach doesn't really allow.

15 Programming Languages

Everyone says assembly is untyped—everyone is wrong

151 points · 80 comments · gingerbill.org

The Odin language creator argues that inline assembly doesn't have to be a stringly-typed escape hatch bolted onto a compiler — Odin's asm implementation treats it as a fully type-checked, callable "template" integrated with the rest of the language's syntax, calling conventions, and register-binding system (clobbers, pinned, tied, scratch registers). He contrasts this with GCC/Clang/Rust's string-based extended asm (where operand references are positional and errors surface late, from the assembler rather than the compiler) and traces older, partially-better approaches like MSVC's statement-based `__asm` (later abandoned at the x64 boundary) and Turbo Pascal's raw-opcode `inline` directive.

What the comments said

  • Commenters pointed out that GCC's extended asm does support named operands via symbolic names, softening one of the article's central complaints, though the author's Odin syntax was still generally agreed to be more readable.
  • Several defended GCC's design as a historically reasonable consequence of needing a uniform way to inject assembly across many wildly different target ISAs, rather than pure incompetence.
  • One detailed critique noted a specific bug in the article's own CPUID example — it fails to bind ECX as an input register despite CPUID needing it — sparking debate over whether Odin's asm binding system genuinely catches such errors or just didn't here.
  • A side debate covered Intel vs. AT&T syntax, with one commenter arguing Intel syntax is objectively more "correct" since it matches vendor documentation, while others argued a unified custom syntax is more valuable when writing assembly across multiple ISAs (e.g. both x86-64 and AArch64).

20 AI & ML

Why your local LLM feels dumber than it is

306 points · 104 comments · forum.level1techs.com

This technical deep-dive argues that a local LLM setup "feeling dumber" than a benchmark-topping model usually isn't the model's fault — every combination of GPU, quantization, attention backend, sampler settings, and chat template produces subtly different results, and the reference lab's benchmark numbers came from hardware and software stacks most home users don't replicate. The author walks through using KL divergence to measure how far a given setup's output-token probability distribution has drifted from a baseline, and starts benchmarking specific variables (like attention-backend precision during prompt prefill) on a Qwen3.6-27B checkpoint, while cautioning that vLLM alone ships hundreds of interacting Python packages, any of which can introduce silent divergence.

What the comments said

  • The single most-cited practical culprit commenters raised was silently mismatched chat templates — many GGUF conversions drop the correct template, causing a silent fallback to ChatML that measurably dumbs down output without any obvious error.
  • A second common culprit was sampler settings: people running whatever their UI defaults to, rather than the settings a model card actually recommends, then wrongly comparing results to benchmark numbers run with proper (often greedy) sampling.
  • Ollama specifically drew criticism for making it easy to not realize you're running a heavily quantized (e.g. Q4) version of a model while believing you're evaluating the "real" model, plus a separate long-standing reputation issue around under-crediting llama.cpp, which it wraps.
  • Several commenters shared enthusiastic firsthand results running recent local models (Qwen3.6/3.8-27B variants) on consumer GPUs via vLLM/sglang/MLX, reporting them as much more capable than expected once configured correctly.
21 Programming Languages

Zig's Io.Threaded is neat

151 points · 92 comments · matklad.github.io

matklad explains why Zig's std.Io.Threaded — a deliberately "boring" thread-based implementation of Zig's new Io concurrency interface — solves a problem he'd wanted solved for years: reliably cancelling a blocking syscall. It uses a POSIX signal-plus-shared-memory-flag protocol (the canceling thread sets a flag then repeatedly signals the target until it acknowledges, causing the blocked syscall to return EINTR and check the flag) to support real cancellation without needing io_uring or tearing down the whole OS thread, unlike Java's checked-but-non-interrupting-of-syscalls interrupt model or POSIX's blunter pthread_cancel.

What the comments said

  • Several readers said the post ends right as it gets interesting, joking that the article itself "got cancelled halfway," and wished for more detail on why avoiding io_uring specifically is desirable.
